# 移动端插件设计指南

> 目标：插件可以在手机端使用，但插件迭代不绑定主包发版。  
> 结论：采用"壳子主包 + 远程内容"设计，插件更新不需要反复打包 App 或重新提交小程序审核。

---

## 一、设计背景

### 1.1 常见痛点

| 痛点 | 说明 |
|------|------|
| App 改动要重新打包和上架审核 | 发布周期长，无法快速迭代 |
| 小程序改动要重新提交审核 | 审核周期 1-7 天，影响插件发布 |
| 插件业务写进主包 | 每次插件迭代都要重发主包 |

### 1.2 设计目标

- **主包长期稳定**：只承载固定能力，不随插件迭代变化
- **插件业务解耦**：插件业务放到 H5 或小程序插件能力
- **插件可热更新**：插件上线、迭代、下线尽量不触发主包发版

---

## 二、推荐架构：壳子 + 远程内容

### 主包职责

| 能力 | 说明 |
|------|------|
| 登录与鉴权 | 获取 token 并维持会话 |
| 设备与通道 | 拉取设备/通道基础数据 |
| 预览与回放 | 调用主系统流媒体接口 |
| 云台与告警 | 使用主系统标准 API |
| 插件入口 | 统一"插件列表"入口，按 URL/类型打开 |

### 主包不负责

- 某个插件的专属业务页面
- 硬编码插件 URL 或逻辑
- 插件特定功能实现

---

## 三、插件在移动端的三种形态

### 形态 A：H5（推荐）

| 特点 | 说明 |
|------|------|
| 实现方式 | 插件提供 H5 页面地址，主包用 WebView 打开 |
| App 端 | 使用 WebView 加载 |
| 小程序端 | 使用 web-view 组件加载 |
| 优点 | 迭代成本最低，跨端一致性最好 |

### 形态 B：微信小程序插件

| 特点 | 说明 |
|------|------|
| 适用场景 | 只做微信生态的插件能力 |
| 注意 | 迭代按微信插件机制走 |

### 形态 C：只扩后端接口

| 特点 | 说明 |
|------|------|
| 实现方式 | 插件只扩展后端数据与接口 |
| 前端展示 | 移动端复用主包现有 UI |

## 四、plugin.json 移动端字段

```json
{
  "id": "my_plugin",
  "name": "我的插件",
  "mobile": {
    "entry_type": "h5",
    "entry_url": "https://example.com/mobile/index.html",
    "entry_url_template": "https://example.com/mobile/index.html?token={token}&tenant={tenant_id}"
  },
  "miniprogram": {
    "entry_type": "webview",
    "entry_url": "https://example.com/mini/index.html",
    "entry_url_template": "https://example.com/mini/index.html?token={token}"
  }
}
```

**字段说明**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `entry_type` | 字符串 | 入口类型：`h5`、`webview`、`native` |
| `entry_url` | 字符串 | 固定地址 |
| `entry_url_template` | 字符串 | 模板地址，由后端替换变量后下发 |

## 五、推荐约定：移动端 H5 路由前缀

如果你的插件 H5 与 PC Web 复用同一个前端工程，建议为移动端准备"更适合手机操作"的路由入口：

| 端 | 示例路由 |
|------|----------|
| PC 端 | `{base_url}/#/visual-command` |
| 移动端 | `{base_url}/#/m/visual-command` |

**说明**：
- 这只是插件端/前端的 URL 约定（例如统一用 `/m/` 表示 mobile）
- 不影响接口与鉴权方案
- 插件更新时只需更新服务器端 H5 或插件包的 `plugin.json`
- **不需要重新打包 App，也不需要重新提交小程序审核**

## 六、移动端插件列表接口

系统提供统一接口获取移动端插件入口：

```
GET /api/v1/plugins/mobile-entries
```

**返回示例**：

```json
{
  "items": [
    {
      "plugin_id": "my_plugin",
      "name": "我的插件",
      "entry_type": "h5",
      "entry_url": "https://example.com/mobile/index.html?token=xxx"
    }
  ]
}
```

**安全建议**：
- 由后端生成最终 `entry_url`，替换敏感参数
- 不让客户端自行拼接敏感参数（如 token）

## 七、鉴权流程

### App 端

1. 用户在 App 登录
2. App 获取 token 并存入内存/本地存储
3. 打开插件 H5 页面时，将 token 作为参数传递
4. H5 页面使用 token 调用主系统 API

### H5 页面鉴权

```javascript
// 从 URL 参数获取 token
const urlParams = new URLSearchParams(window.location.search)
const token = urlParams.get('token')

// 调用主系统 API
fetch('/api/v1/devices', {
  headers: {
    'Authorization': `Bearer ${token}`
  }
})
```

## 八、开发与交付建议

### 对插件开发者

| 建议 | 说明 |
|------|------|
| 业务优先放 H5 | 不依赖主包发版 |
| 保持字段定义稳定 | 便于主包适配 |
| 准备最小化交互页面 | 减少跳转复杂度 |
| 测试多端兼容性 | App WebView / 小程序 web-view / 移动端浏览器 |

### 对主包开发者

| 建议 | 说明 |
|------|------|
| 只做"列表 + 打开入��" | 不写死插件逻辑 |
| 统一处理 token 过期 | 引导用户重新登录 |
| 处理异常页面 | 网络错误、H5 加载失败等 |

## 九、高频坑点

| 坑点 | 解决方案 |
|------|----------|
| URL 域名未加入小程序合法域名白名单 | 在微信公众平台配置服务器域名 |
| H5 页面跨域配置不完整 | 在 H5 服务端配置 CORS |
| entry_url 模板变量未替换 | 确认后端生成 URL 时正确替换 |
| 插件入口写死在主包 | 改为动态拉取插件列表 |

## 十、验收清单

上线前至少验证：

| 序号 | 验收项 | 验证方法 |
|------|--------|----------|
| 1 | 插件列表可正确拉取 | 调用 `/api/v1/plugins/mobile-entries` |
| 2 | App 端能打开插件页面 | 在 App 中打开插件入口 |
| 3 | 小程序端能打开插件页面 | 在小程序中打开插件入口 |
| 4 | token 过期后可恢复登录 | 过期后引导重新登录 |
| 5 | 插件版本更新不需要主包重发 | 更新 H5 后 App 无需发版 |

# 视频点播与播放问题详解

> 本文档深入分析视频点播全流程，从信令交互到流媒体传输，帮助你定位和解决播放类问题。
> 适合有网络基础的运维人员阅读。
> 更新时间：2026-04-13

---

## 1. 点播全流程解析

理解播放问题的前提是清楚一次完整的点播过程发生了什么：

### 1.1 时序图

```
┌──────────┐     ┌──────────────┐     ┌────────────┐
│  Web用户  │     │  PyGBSentry   │     │   设备     │
│ (浏览器)  │     │   (信令服务)   │     │ (IPC/NVR) │
└────┬─────┘     └──────┬───────┘     └─────┬──────┘
     │                  │                    │
     │  1. 点击播放      │                    │
     │ ────────────────>│                    │
     │                  │                    │
     │                  │  2. INVITE (SDP)   │
     │                  │ ──────────────────>│
     │                  │                    │
     │                  │   3. 200 OK (SDP)  │
     │                  │ <──────────────────│
     │                  │                    │
     │                  │   4. ACK          │
     │                  │ ──────────────────>│
     │                  │                    │
     │                  │                    │  5. 设备开始发流 (RTP)
     │                  │                    │
     │                  │ <═══════════════════════════> ZLM (流媒体)
     │                  │                    │
     │  6. 返回播放地址  │                    │
     │ <─────────────── │                    │
     │                  │   7. 无人观看时    │
     │                  │   Bye → 停止发流   │
     │                  │ ──────────────────>│
     │                  │   8. 200 OK        │
     │                  │ <──────────────────│
```

### 1.2 各阶段说明

| 阶段 | 操作 | 成功标志 | 常见问题 |
|------|------|----------|----------|
| ① | Web 点击播放按钮 | 前端发送请求 | JS 报错 |
| ② | 发送 INVITE（带 SDP） | 设备收到请求 | 400/408 错误 |
| ③ | 设备回复 200 OK（带 SDP） | 协商成功 | 无响应/超时 |
| ④ | 发送 ACK 确认 | 设备开始准备 | 无 ACK |
| ⑤ | 设备发流 → ZLM | ZLM 收到流 | 收流超时 |
| ⑥ | 返回播放地址 | 播放器开始拉流 | 无地址 |
| ⑦ | 无人观看自动停止 | Bye 发送成功 | 流持续发送 |

## 2. 错误分类与定位

### 2.1 分类总览

| 类型 | 典型表现 | 错误码 |
|------|----------|--------|
| **信令错误** | 点击播放后很快（<1秒）报错 | 400, 408, 500 |
| **收流超时** | 等待很久后超时 | timeout |
| **流解析失败** | 黑屏或花屏 | 无报错但无声无影 |
| **播放卡顿** | 能播放但画面断断续续 | 无报错 |

## 3. 信令错误详解

### 3.1 400 Bad Request

**表现：** 点击播放后瞬间弹出 400 错误，通常在 1 秒内。

**原因：** 设备认为 INVITE 消息格式错误或内容不完整。

**排查步骤：**

1. **抓包分析**

```bash
# 在服务器抓取 SIP 信令
tcpdump -i any -n port 5060 -c 200 -w /tmp/sip_invite.pcap

# 同时在前端触发一次点播

# 用 Wireshark 打开，查看 INVITE 消息是否包含所有必需字段：
# - Via
# - From / To
# - Call-ID
# - CSeq
# - Contact
# - SDP (v, o, s, c, t, m)
```

2. **常见 400 原因**

| 原因 | 现象 | 解决 |
|------|------|------|
| SDP 中 IP 地址格式错误 | c= 行含内网 IP | 确认收流 IP 配置 |
| 端口号超出范围 | m= 行端口非法 | 确认 RTP 端口范围 |
| 设备固件不兼容 | 特定型号必现 | 升级固件或联系厂商 |
| ZLM 未配置 | 设备无法识别 | 配置 ZLM hook |

3. **案例：海康设备返回 400**

**排查记录：**
- 设备：某型号海康摄像机
- 现象：点播必返 400
- 抓包：INVITE 中 c= 行 IP 为 `0.0.0.0`

**解决：** 在平台侧修改设备「收流 IP」为服务器实际 IP，重新点播成功。

---

### 3.2 408 Request Timeout / 点播超时

**表现：** 点击播放后等待 30 秒到 3 分钟，然后报错「点播超时」。

**原因：** 设备在规定时间内未响应 INVITE 请求。

**排查步骤：**

```
① 设备真的收到了 INVITE 吗？
   └─ telnet 服务器IP 5060 → 不通 → 防火墙未放行
   └─ telnet 通 → 继续下一步

② 设备收到了但无法处理？
   └─ 抓包确认设备 IP
   └─ 确认设备网络状态

③ NAT 环境下，路由 NAT 表老化
   └─ 缩短心跳周期至 30 秒
   └─ 确认 SIP 信令和流走同一路径
```

**关键日志搜索：**

```bash
# 搜索超时相关日志
grep -E "timeout|INVITE|device" logs/app.log | grep -i "timeout"

# 搜索设备响应记录
grep "200 OK" logs/app.log | grep -v "heartbeat" | tail -20
```

---

### 3.3 500 Internal Server Error

**表现：** 设备返回 5xx 错误。

**原因：** 设备内部处理异常。

**解决：**
1. 查看设备固件版本，升级到最新
2. 联系设备厂商客服，提供抓包文件
3. 确认设备时间是否正确（时间偏差过大可能影响信令）

## 4. 收流超时详解

### 4.1 什么是收流超时

收流超时发生在步骤 ③（设备回复 200 OK）之后，设备已经开始发流，但 PyGBSentry（ZLM）未能在超时时间内收到 RTP 流。

### 4.2 排查路径

```
收流超时
├── 设备是否真的在发流？
│   ├─ 是，ZLM 没收到 → 检查 ZLM 是否正常监听
│   └─ 否，设备没发流 → 设备侧配置问题
│
├── ZLM 是否正常？
│   ├─ curl http://localhost:9092/api/getServerConfig → 失败
│   └─ 重启 ZLM
│
├── ZLM 的 hook 配置是否正确？
│   ├─ hook.admin_params 是否配置？
│   ├─ hook.on_publish 是否回调到 PyGBSentry？
│   └─ 服务器能否访问 hook 地址？
│
├── SDP 中收流地址是否正确？
│   ├─ 公网部署时 c= 行是否为公网 IP？
│   └─ 内网部署时 c= 行是否为内网可达 IP？
│
└── 防火墙是否放行了 UDP RTP 端口？
    └─ nc -zvu 服务器IP 30000 → 需返回 succeeded
```

### 4.3 ZLM 日志分析

```bash
# 查看 ZLM 是否收到流
docker exec pygbsentry-media tail -n 200 /opt/zlmediakit/log/log.txt | grep -i rtp

# 期望看到类似：
# [RtpServer] new RTP connection from: 192.168.1.100:5060
# [RtpServer] recv RTP data from 192.168.1.100:30001
# [multiMediaSource] stream registered: rtp://stream_key
```

如果没有收到流记录，说明：
- 防火墙拦截了 UDP RTP 端口
- SDP 中收流 IP 配置错误
- 设备发流到了错误地址

## 5. 抓包实操指南

### 5.1 使用 tcpdump 抓包

```bash
# 抓取 SIP 信令（5060 端口）
tcpdump -i any -n port 5060 -c 500 -w /tmp/sip.pcap

# 抓取 UDP RTP 流（媒体端口）
tcpdump -i any -n port 30000:40000 -c 1000 -w /tmp/rtp.pcap

# 抓取 eth0 网卡上的所有相关流量
tcpdump -i eth0 -n \( port 5060 or port 30000:40000 \) -c 500 -w /tmp/all.pcap
```

### 5.2 使用 Wireshark 分析

安装 Wireshark 后打开 `.pcap` 文件：

1. **过滤 SIP 信令：** `sip`
2. **过滤 INVITE：** `sip.Method == "INVITE"`
3. **过滤 RTP 流：** `rtp`
4. **查看 SDP 内容：** 右键 INVITE → 分析 → 展开 SDP

**关键 SDP 字段：**

```
v=0                           ← 版本
o=- 123456 123456 IN IP4 xxx   ← 会话标识
s=Play                         ← 会话名称（Playback/Play）
c=IN IP4 192.168.1.100        ← 媒体连接地址（重要！）
t=0 0                          ← 时间
m=video 6000 RTP/AVP 96       ← 视频媒体描述（端口=6000）
a=rtpmap:96 H264/90000         ← 视频编码
```

**c= 行 IP 地址是关键：**
- 如果是 `0.0.0.0` → 设备使用对称NAT模式，ZLM 收流地址不对
- 如果是公网 IP 但服务器在内网 → 设备无法路由到服务器
- 如果是服务器实际监听 IP → 地址正确，继续排查防火墙

## 6. 播放地址说明

### 6.1 播放地址格式

点播成功后，平台会返回多种格式的播放地址：

| 协议 | 地址格式 | 适用场景 |
|------|----------|----------|
| **WebSocket-FLV** | `ws://IP:PORT/live/stream_id` | 浏览器播放（推荐，低延迟） |
| **HTTP-FLV** | `http://IP:PORT/live/stream_id.flv` | 浏览器播放（兼容性好） |
| **HLS** | `http://IP:PORT/live/stream_id.m3u8` | 移动端/iOS Safari |
| **RTSP** | `rtsp://IP:PORT/live/stream_id` | 桌面播放器（VLC） |
| **RTMP** | `rtmp://IP:PORT/live/stream_id` | 推流/直播平台 |

### 6.2 地址能否播放的判断

| 地址类型 | 能否播放 | 判断条件 |
|----------|----------|----------|
| WebSocket-FLV | 取决于 | ZLM 是否编译了 FFmpeg |
| HTTP-FLV | 取决于 | ZLM 是否编译了 FFmpeg |
| HLS | 通常可播放 | 需要设备码流稳定 |
| RTSP | 通常可播放 | VLC 播放 |
| RTMP | 需要推流端 | 用于转推到其他平台 |

### 6.3 直接获取播放地址

在设备「通道列表」页面，点击「更多地址」可以查看所有格式的播放地址。

## 7. 特殊场景

### 7.1 NAT 环境下的点播

**问题：** 服务器在内网，设备在公网，点播失败。

**原因：** INVITE 消息中 SDP 的 c= 行 IP 地址可能是内网地址，设备发流时无法路由到内网。

**解决：**

1. **方案一：配置 NAT 穿透**
   - 在平台配置公网映射地址
   - SIP 信令和 RTP 流都走公网

2. **方案二：使用 TCP 模式**
   - 在设备侧开启 TCP 发流
   - TCP 天然支持 NAT 穿透

3. **方案三：反向代理**
   - 使用支持 NAT 穿透的流媒体方案

### 7.2 多流媒体节点时的点播

**问题：** 部署了多个 ZLM 节点，点播路由不准确。

**原因：** ZLM 节点的 hook 配置未正确指向 PyGBSentry。

**排查：**
1. 确认每个 ZLM 节点的 `hook.on_play` 和 `hook.on_publish` 都回调到 PyGBSentry
2. 确认 PyGBSentry 配置了所有 ZLM 节点的 ID 和地址
3. 查看「节点管理」页面，确认节点状态

## 8. 快速排查清单

遇到播放问题时，按以下清单逐项检查：

```
□ 1. 设备在线吗？（离线 → 先解决注册问题）
□ 2. 点击播放后有响应吗？（无响应 → 信令层面问题）
□ 3. 错误码是多少？（400/408/500 → 对应章节排查）
□ 4. ZLM 日志有流记录吗？（无 → 防火墙/收流地址问题）
□ 5. SDP 中 c= 行 IP 是什么？（确认地址正确）
□ 6. 防火墙放行了 UDP 30000-40000 吗？（确认端口可达）
□ 7. 浏览器控制台有报错吗？（JS 层面问题）
□ 8. 换个设备/通道能播放吗？（排除设备问题）
□ 9. 换成 TCP 模式能播放吗？（NAT 问题）
□ 10. 重启 ZLM 能解决吗？（临时恢复）
```

## 9. 配置参考

### 9.1 SIP 信令超时配置

```yaml
# backend .env
SIP_INVITE_TIMEOUT: 30      # INVITE 超时（秒）
SIP_ACK_TIMEOUT: 10         # ACK 等待超时（秒）
RTP_RECV_TIMEOUT: 30        # 收流超时（秒）
```

### 9.2 ZLM hook 配置

```ini
[hook]
enabled=1
admin_params=secret=your_hook_secret
on_publish=http://your_server_ip:8000/api/v1/ops/zlm/hook
```
